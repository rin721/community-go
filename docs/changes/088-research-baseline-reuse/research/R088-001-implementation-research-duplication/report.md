# R088-001：实施入口重复研究缺口

## 1. 研究问题与方法

本研究回答：方案已经由当前代码事实和可复核证据推导出来后，实施阶段为什么还会出现“核对当前代码事实”，以及如何避免它扩展为重复的全量研究。

方法是复核根 `AGENTS.md`、`docs/research/README.md`、013 的研究门禁设计，再对照 087 的研究报告、任务清单与用户提供的实施任务截图。这是仓库流程治理问题，内部主源足以回答，不需要联网或外部框架调研。

## 2. 已验证事实

### 2.1 研究阶段已要求完成事实核对

`AGENTS.md` 要求研究从当前代码、配置、测试、运行入口和 Git 事实开始；研究门禁只有在关键问题具有可复核证据后才能通过。013 也要求当前代码、配置、测试、入口和 Git 事实按任务相关性完成核验。

因此，“研究完成”后再无条件地全量追踪同一代码，不是当前状态机的必需步骤。

### 2.2 现有规则只规定了“何时回退”，没规定“如何廉价判定”

`AGENTS.md` 已规定新证据推翻研究结论时返回研究，`metadata.yaml` 也要求记录证据快照与 `refresh_triggers`。但现有规则没有说明实施入口应先比较“快照后哪些路径变了”，再判断是否命中触发器。

缺少这一判定算法时，实施者容易用“再读一遍全部相关文件”来规避风险，从而造成用户看到的重复。

### 2.3 087 本身已完成结构事实研究

R087-001 已追踪 `AppShell -> WorkspaceProvider -> WorkspaceOutlet -> Routes -> SettingsLayout`，并从当前代码、历史设计和 E2E 得出 Settings 被拆成八个 mounted panel 以及 Accounts location 被重放的结论。`tasks.md` 也已将 `RES-087-001` 标记完成。

截图中实施计划再列出“核对当前代码事实：contract、AppShell、workspace、routes…”。如果这表示再次全量追踪，它与已完成的 `RES-087-001` 重复；只有它表示快照后增量漂移判定时才是必要的实施入口检查。

### 2.4 失败用例不等于重做研究

087 未得到带认证界面中的具体 `event.target` 证据，所以计划在实施第一步建立失败用例。该用例用于限定能够宣称修复的具体行为，不需要重做 workspace 资格方案比较。只有复现结果推翻了方案前提，它才变成新研究输入。

## 3. 推断与目标规则

实施入口应当使用一个有界算法：

```text
研究快照 + 当前 revision/Git 状态
  -> 快照后是否有研究范围内的变更？
     -> 否：记录基线未漂移，直接实施
     -> 是：是否命中 refresh_triggers 或否定前提？
        -> 否：保护增量变更，继续实施
        -> 是：只定向复核受影响结论
           -> 前提成立：继续实施
           -> 前提失效：返回研究/计划门禁
```

该算法不允许以“保证稳妥”为由无条件全量重读。它也不删除必要验证：失败用例证明修改前问题，修改后测试证明验收标准，而研究回答方案前提和选择理由。

## 4. 适用边界与局限

本结论适用于已经通过研究门禁并形成计划的同一任务。它不适用于首次研究，也不允许忽略用户已有变更、已明确命中的刷新触发器或修改后必要验证。

人工编写的 `refresh_triggers` 可能遗漏。如果增量 Diff 直接显示研究前提已失效，即使未字面命中触发器，也必须定向复核。这是对漂移证据的响应，不是因阶段切换而重做研究。

## 5. 研究门禁结论

研究门禁通过。问题根因、重复边界、增量判定算法、回退条件和验证边界都有当前仓库证据，没有阻碍形成 088 纯文档计划的未知项。
