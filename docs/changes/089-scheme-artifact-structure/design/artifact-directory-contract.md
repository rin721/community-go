# 目录、内容与状态契约

## 1. 固定目录布局

```text
docs/changes/<seq-num-name>/
├── README.md
├── research/
│   ├── README.md
│   └── Rxxx-<semantic-name>/
│       ├── metadata.yaml
│       └── report.md
├── requirements/
│   ├── README.md
│   └── <business-topic>.md
├── design/
│   ├── README.md
│   └── <technical-topic>.md
└── tasks.md
```

`requirements.md` 和 `design.md` 不再是新方案的固定入口。目录名本身表达产物类型，目录中的 `README.md` 提供稳定链接入口。

## 2. 需求目录契约

`requirements/README.md` 必须包含需求摘要、阅读顺序、受众和边界，并链接所有需求分篇。入口之外至少有一份实质性需求文档；存在多个独立业务主题、用户角色、流程或验收域时继续拆分。

需求分篇使用客户语言，优先描述：

- 客户目标和待解决问题；
- 用户角色、使用场景和可观察行为；
- 范围、约束、非目标与风险；
- 稳定需求 ID 和可验证验收标准。

外部协议、合规或兼容限制确实影响客户时可以出现技术名称，但应解释成客户可判断的能力或限制。内部接口、包路径、资源 owner 和调用顺序不进入需求正文。

## 3. 设计目录契约

`design/README.md` 必须包含设计摘要、关键决策、阅读顺序，并链接全部详细设计。入口之外至少有一份实质性详细设计；存在多个模块、状态机、数据域、入口、迁移阶段或验证域时按技术主题拆分。

详细设计根据任务适用性覆盖：

- 当前边界、目标边界、依赖方向和 composition 位置；
- 公共与内部接口、输入输出、不变量和版本语义；
- 数据结构、数据流、控制流、状态转换和生命周期；
- 资源所有权、并发、取消、超时、重试和清理；
- 错误分类、失败传播、降级、日志、诊断与低敏边界；
- 配置、默认值、迁移、兼容和退役路径；
- 受影响文件、测试层次、失败用例、回归和验收证据。

不适用的主题可以省略或说明不适用原因；不能用“按现有方式处理”等模糊表述代替任务关键设计。

## 4. 任务清单契约

`tasks.md` 是唯一状态账本。每个任务使用稳定 ID 和 checkbox：

```markdown
- [ ] `APP-001` 实现已确认的装配变更。依赖：`PLAN-001`；完成条件：相关测试与文档同步通过。
- [x] `VER-001` 验证文档链接。证据：`./scripts/Verify-Docs.ps1 -BaseRef HEAD` 通过。
```

`[ ]` 表示尚未满足完成条件；`[x]` 表示完成条件和证据均已满足。可以使用段落或子项补充依赖、确认状态、Commit 和风险，但不得再用表格状态或自然语言“完成”建立第二套状态。

## 5. 链接与单一权威

变更根 `README.md` 按“研究 -> 需求 -> 设计 -> 任务”给出阅读顺序。需求链接设计时只指向 `design/README.md`，设计链接需求时只指向 `requirements/README.md`；任务通过稳定 ID 引用需求和设计，不复制大段正文。

方案实施完成后，当前有效行为仍同步到主题 authority；变更目录继续作为历史证据，不成为第二套当前规范。
