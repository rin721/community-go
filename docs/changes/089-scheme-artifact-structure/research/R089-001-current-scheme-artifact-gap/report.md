# R089-001：当前方案产物结构缺口

## 1. 研究问题与方法

本研究回答：如何让每个新方案稳定产出需求、设计和任务，同时区分受众、保证详细设计深度，并避免内容增长后继续堆在单个文件中。

方法是核对根 `AGENTS.md`、`docs/changes/README.md` 的当前强制结构，抽查 012 的大型方案拆分方式，并把用户本轮明确的产物受众和状态表达作为决策输入。本任务只调整仓库文档治理，不需要外部技术选型或联网研究。

## 2. 已验证事实

### 2.1 当前固定结构仍以单文件为中心

修改前的 `AGENTS.md` 明确要求每项新变更包含 `requirements.md`、`design.md` 和 `tasks.md`。它定义了三类内容，但没有规定需求面向客户、设计面向技术人员，也没有保证详细设计能够按主题扩展。

### 2.2 大型方案已经证明目录拆分有实际需要

012 在 `requirements.md` 和 `design.md` 之外又增加了 `requirements/` 与 `design/`，其中设计按配置、生命周期、模块边界、错误与迁移等主题拆分。这证明大型方案需要多文件承载。

但 012 仍以根单文件作为入口，子目录没有自己的 `README.md`；该做法是历史扩展结果，不是所有新方案都遵守的稳定契约，也容易形成“主文件继续增长、目录只是附件”的双重入口。

### 2.3 当前任务状态表达不统一

现行规则允许 `tasks.md` 通过表格文字记录“完成”，历史任务也同时存在表格状态和 checkbox。用户本轮明确要求任务是标记完成清单，因此规则需要把 Markdown checkbox 设为唯一完成状态，而不是只要求存在任务文件。

## 3. 推断与目标规则

需求和设计应从“单文件加可选附件”改为“目录即产物”：

```text
requirements/README.md -> 客户可读摘要与导航 -> 业务语义需求分篇
design/README.md       -> 技术决策摘要与导航 -> 技术主题详细设计分篇
tasks.md               -> 稳定任务 ID + [ ]/[x] + 完成条件与证据
```

目录入口负责帮助目标受众找到内容，不承担全部正文。每个目录至少有一份入口之外的实质性明细，确保目录不是给单文件换壳；多个独立主题继续按语义拆分，避免产生新的超大 `README.md`。

需求只描述客户能理解和验收的目标、场景、范围、限制与风险。内部模块、接口、数据流、状态机、错误、资源、配置、迁移和测试设计进入 `design/`。任务只跟踪执行状态，不重复需求或设计正文。

## 4. 适用边界与迁移

本规则适用于生效后新建的方案。历史变更保留原结构，以免制造无业务收益的大规模链接迁移；历史任务需要实质性重做方案时，应建立新变更记录并使用新结构。

只读分析若不形成方案，仍可按现有门禁只交付研究报告。研究档案也不替代三类方案产物。

## 5. 局限与剩余未知

不同任务需要的需求和设计主题不同，规则不能强制一套与业务无关的固定章节。它通过“入口之外至少一份语义明细”和适用性清单保证深度，同时允许按真实任务选择拆分页。

当前文档校验脚本主要验证链接和 metadata，没有自动检查新方案目录及 checkbox。此次是纯文档规则更新，不在未确认情况下修改脚本；后续若需要自动门禁，应另立非文档方案。

## 6. 研究门禁结论

研究门禁通过。现状、历史案例、目标受众、目录结构、任务状态和历史迁移边界已有可复核依据，没有阻碍形成 089 纯文档计划的未知项。
