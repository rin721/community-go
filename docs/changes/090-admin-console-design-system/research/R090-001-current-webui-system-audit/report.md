# 当前 Web UI 系统审计

## 1. 研究结论

当前 Web UI 已经不是“没有组件、没有 Token”的空白项目。它有 AppShell、导航、工作区、40 余个共享 UI 导出、响应式变量和多类业务页面。问题在于这些能力没有形成一套可预测的后台产品系统：页面能拼出来，但壳层、页面层、功能层和状态层各自表达一次层级，导致空间被容器与标题消耗，真正的数据和操作反而退居次要位置。

因此，继续在业务页面增加 Card、间距或颜色不会解决根因；需要从页面骨架和功能模式层重构。

## 2. 直接视觉证据

审阅范围包括 `086-shell-geometry-dashboard.png`、083 的 accounts/roles/settings/audit/dashboard 截图、084/085 工作区截图，以及桌面亮色、笔记本暗色和移动端样例。

### 2.1 空间分配失衡

- 1280px 截图中，展开侧栏约 264px，单独占据约 20.6% 宽度；设置页再叠加约 208px 的局部导航，导航合计接近 37%，主工作区变得狭窄。
- 64px Header 与 42px 工作区栏叠加；OpenAPI 只有一个宿主工作区时仍出现工作区层，与页面标题和页内页签重复表达位置。
- 页面通常经历“全局面包屑 → PageHeader eyebrow/title → PageSection kicker/title → Card/Table header”四级重复，数据首屏位置被明显推低。
- 筛选器常占两行且对齐关系弱，结果数量、清除操作和主操作分散，用户需要扫描多个区域才能理解当前查询状态。

### 2.2 视觉层级依赖容器而非内容

- 大面积浅灰底上不断叠加白色 Card，Card 成为默认排版工具，而不是需要边界、分组或浮层语义时才使用的容器。
- Dashboard 指标使用洋红、紫、青、橙等装饰性色块，颜色表达“模块不同”而不是“状态、风险或重点不同”，削弱语义稳定性。
- 表头偏弱、行高和单元格留白偏大；行内同时出现“查看详情”和更多菜单，操作密度与优先级不清晰。
- 大写蓝色 kicker 在多个层级重复，形成视觉噪声；真正的页面标题、状态和关键操作反而没有足够的权重差。

### 2.3 响应式不是缩放，而是结构失败

- OpenAPI 移动截图中，固定双栏仍横向存在，右侧内容被裁切，长 revision 文本溢出。
- 顶栏把搜索、全屏、语言、主题、配色、账户等桌面能力一并压到窄屏，没有进行优先级折叠。
- 暗色选中态使用高饱和蓝，输入区趋近纯黑，局部对比过强而页面级层级不足。

这些问题说明移动端缺少独立的内容优先级和模式切换规则，不是补几个 media query 就能修复。

## 3. 前端结构证据

### 3.1 共享组件数量多，但缺少真正的功能模式

`webui/src/ui/index.tsx` 集中导出 PageHeader、Surface、Button、DataToolbar、DataTable、FilterBar、DetailDrawer、TreeView、MetricCard 等 40 余项能力。典型账户、角色、Token 页面仍各自组合 10—20 个基础组件、维护本地查询状态和操作流程。

这意味着当前复用主要发生在 DOM 和外观层，尚未沉淀为以下稳定功能模式：

- 资源列表的查询、筛选、选中、批量操作、分页和刷新；
- 实体详情的摘要、关系、活动、配置和危险操作；
- 设置表单的 dirty 状态、保存反馈和离开保护；
- 批量操作的确认、进行中、部分失败和结果追踪；
- 初次加载、后台刷新、无数据、无匹配、无权限和服务异常的状态矩阵。

### 3.2 巨型 UI 入口混合了不同职责

单个 UI 文件同时承担设计原语、布局、表格、表单、反馈、图表、i18n 文本和业务工作流，导致：

- 组件依赖和变更影响面难以判断；
- 第三方能力被重复封装，项目边界反而变宽；
- 页面为了特殊情况继续向万能组件增加参数；
- 很难为单一模式做隔离测试、文档示例和视觉回归。

具体风险包括：Button 把 `onPress` 重新适配为伪 DOM `onClick`；SearchInput 把受控输入值与延迟查询回调耦合，可能造成输入反馈滞后；搜索图标使用 emoji 而非统一图标系统；TreeView 声明 tree 角色却未呈现完整的方向键与 roving focus 行为。

### 3.3 Token 已存在，但没有成为唯一规格来源

`styles.css` 已有 primitive、semantic、component 等变量层次，这是可保留的方向。但当前样式仍存在：

- 主样式文件超过 3000 行，模块 CSS 继续分别积累；
- 数百个 `px` 字面量与多处直接颜色值；
- 共享组件使用 `text-[10px]`、`min-h-[64px]`、`px-5` 等任意 Tailwind 值；
- 暗色与主题预设重复硬编码，而不是通过稳定语义 Token 映射；
- 业务页面仍可自行决定宽度、圆角、间距和行高。

结论不是删除 Token，而是缩小 Token 层级、建立消费边界并让布局与组件只能通过语义规格取值。

### 3.4 页面数据状态不统一

项目已经引入 TanStack Query、React Hook Form 和 Zod，但并非所有资源页都通过统一查询和表单边界运行；仍有页面手工维护 `useState/useEffect`、请求、错误和刷新。这会让缓存、取消、后台刷新、查询参数、失效策略和反馈文案在页面间不一致。

## 4. 信息架构与功能表达问题

- Sidebar 中分组父项同时承担导航与展开控制，父子可能同时高亮，当前位置不唯一。
- 顶栏容纳过多低频个性化工具；高频的当前位置、全局搜索、环境/健康状态和通知没有形成清晰优先级。
- 大多数页面以“标题 + Card + Table/Form”描述能力，缺少对业务对象生命周期、关系、风险和下一步的表达。
- 详情经常退化为 Drawer 中的字段列表，无法承载关联资源、活动记录、权限影响和危险操作。
- Dashboard 更像组件展示页，缺少“需要关注什么、为什么、接下来做什么”的运营叙事。

## 5. 事实、推断与未验证项

### 当前事实

- 当前技术栈和共享 UI、Token、页面及截图均可在仓库中定位。
- 本地 `127.0.0.1:5173` 未监听，因此本轮没有改变进程状态去启动应用。
- 087 在研究收尾时已提交为 `47d2d9a`；定向复核确认普通路由回到单一 Outlet、OpenAPI 保留显式 singleton，但存在 workspace 时宿主仍会渲染独立标签栏。

### 基于证据的推断

- 视觉不舒适的主因是层级和空间模型，而不是某个色值或某张卡片。
- 如果继续以 PageSection 默认套 Card、页面各自维护查询和详情，新增模块会放大不一致。
- 组件库整体替换并不能自动解决业务模式缺失；需要重新定义项目自有组件边界。

### 实施期仍需验证

- 真实数据量下的表格密度、列宽和虚拟化阈值；
- 完整键盘操作、读屏和对比度结果；
- 典型桌面、笔记本、平板、手机的运行态交互；
- 页面加载性能、缓存策略和长列表性能。

## 6. 对本任务的影响

方案必须先建立统一 PageFrame 和后台功能模式，再迁移页面；不能从某个页面局部“美化”开始。实施顺序应是依赖单轨化 → Token 消费边界 → Shell/PageFrame → 原语与模式组件 → 页面族迁移 → 后端补强 → 多模态与自动化验收。
